# Your Files and Privacy

Before you upload personal files, you may want to know where they are encrypted, who can read them, and what happens if you lose your password. This guide explains the protection shown in this repository and the limits you should understand.

## How are my files protected?

Your browser encrypts file contents before upload. Each file has an independent random key, and its chunks are encrypted using AES-GCM. On download, the client checks integrity and decrypts the chunks to reconstruct the content.

File names, paths, and per-file keys are also encrypted. A vault key generated by the client protects this metadata; your separate encryption password protects the vault key. The server stores ciphertext and encrypted key material.

Having the server's file chunks alone is therefore not the same as having readable originals. Recovery also requires the appropriate keys and metadata.

## What can the server see?

File encryption does not hide every detail of your account or activity.

- **Encrypted:** file contents, file names, paths, and per-file keys within metadata.
- **Still processed by the server:** email addresses, usernames, sign-in password hashes, sessions, file ownership, related timestamps, ciphertext sizes, some original logical sizes, chunk counts, and category hints.
- **Outside file encryption:** account avatars.

An encrypted file space is not an anonymous service. HTTPS remains important.

## Why are there two passwords?

Your sign-in password verifies account access. Your encryption password unlocks your encrypted space.

Resetting a sign-in password does not replace the keys needed to decrypt files. Choose a long, unique encryption passphrase and keep it safe. A weak password may still be guessed; using encryption does not remove that risk.

## What if I forget my encryption password?

Access depends on whether you still have another usable unlocking method, such as a previously configured Passkey supported by your current device. Being able to sign in does not necessarily mean you can unlock your files.

If all usable unlocking methods and keys are lost, server-side ciphertext alone cannot directly restore the files. Before changing devices or clearing a password manager, confirm that your new setup can unlock your space. Keep an independent backup of irreplaceable files.

## What does a Passkey do?

A Passkey can participate in account authentication. Where supported and configured, it can also protect and unlock vault-key material.

Availability depends on your browser, operating system, password manager, and authenticator. A registered Passkey is not a guarantee that every device can unlock your space.

## Does uploading change file quality?

The promise "No compression, no speed limits, no transcoding" describes the intended user experience. Here, "no compression" means **no lossy compression or quality reduction**, not that the transfer format never uses compression. Your photos, videos, and other files are not re-encoded into a different media format as part of this upload process.

Internally, the browser can apply **lossless gzip compression** to individual chunks before encryption. It uses the compressed payload only when gzip is supported and the result is smaller; otherwise, it keeps the original chunk payload. This reversible storage and transfer step does not discard file content or reduce image resolution, video frame rate, or media quality.

When you download a file, the client decrypts the chunks, automatically decompresses any gzip-compressed payloads, and reassembles the original file. You do not receive a gzip archive and do not need to unzip anything yourself. For an unchanged file, successful reconstruction restores the original bytes. You can check this by comparing SHA-256 hashes of the original and downloaded files; matching hashes confirm byte-for-byte equality.

"No speed limits" refers to the service's advertised absence of an artificial transfer-speed cap, not a promise of a particular speed or unlimited resources. Actual throughput still depends on your connection, device, encryption and compression work, server capacity, and storage service. It should not be read as removing storage quotas or other service limits.

In short: **original file content and quality are preserved, without lossy compression or transcoding. Optional lossless gzip is automatically reversed on download.**

## What should I do to stay safe?

Encryption cannot protect a device already controlled by malicious software. Your browser must handle readable content while you unlock and view files, so device security, browser extensions, and the site you visit matter.

A website supplies the JavaScript your browser runs. If it supplies maliciously modified code, your passwords or unlocked content may be at risk. The repository lets you inspect this implementation, but does not independently establish that the website delivered the same code during a particular visit.

- Use trusted devices and current browsers.
- Be careful with extensions that can read page contents.
- Check the website address and use HTTPS.
- Never share encryption passwords, recovery links, or usable key material.
- Keep separate backups; encryption is not a guarantee against data loss.

## Where are the technical details?

In [the client implementation](public/app.js), look for:

- `derivePasswordWrappingKey` and `wrapVaultKey`: PBKDF2-SHA256 with 600,000 iterations and vault-key wrapping.
- `prepareEncryptedUpload` and `encryptMetadata`: random file keys and metadata protection.
- `chunkIv`, `chunkAad`, and `encryptChunk`: chunk indices, authenticated data, and AES-GCM.
- `decodeFileChunk`: reconstruction after decryption.

Important review areas include key/IV reuse across editing, retries and resumption; integrity verification; authorization; concurrency; and boundary handling. These are review priorities, not a claim that every path has been independently audited.

## How do I report a problem?

General code questions are welcome in Issues. If a finding contains sensitive details, contact the [maintainer](https://github.com/yuniaries) to arrange a private channel before sharing it.

Do not include real passwords, recovery links, keys, databases, or user files in a public report.
